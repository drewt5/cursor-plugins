# Internal retained package storage

`stagePackage({ source, root })` in `scripts/lib/installation-storage.mjs` copies only the portable payload into an unpredictable `.pstack/releases/.stage-*` directory on the installation filesystem. It preserves file modes, checks the canonical byte/executable-mode digest and source stability, writes detached provenance, and renames the complete payload to `.pstack/releases/<digest>`. It verifies all stored files and rejects symlinks, unexpected files, digest changes and provenance mismatches. An existing digest directory is inspected; its name alone is never proof. Reusing identical verified content retains that stored copy's provenance rather than inventing a new origin for unchanged bytes.

Staging does not publish a receipt, replace `.pstack/package`, activate host files, migrate legacy directories, or delete old releases. Failed staging removes only its own unpredictable scratch directory; it may leave empty storage parents. Callers will serialize mutation with the scoped installation lock. This internal API is not a public update command.

`verifyGeneration(root, generation)` validates a retained descriptor against the fixed local storage path. `renderStagedArtifacts({ root, generation, targets, opencodeRoot, global, config, hostObservations })` calls that verified payload's retained `scripts/lib/installation-artifacts.mjs:renderArtifacts` contract 1. It accepts the current effective model configuration and proposes artifacts without writing configuration or invoking providers. Only the supported current/previous generation and the explicit legacy migration baseline are recovery inputs; arbitrary historical renderer compatibility is not promised. Recovery execution is supplied by #18, not this renderer contract.

Proposed artifacts refer to the stable `.pstack/package` path, a relative link to the selected local generation. Host skill links, OpenCode command instructions and agent references use this location, so project relocation and source-checkout removal preserve references. Write operations use the real `.pstack/releases/<digest>` path and replace the stable link itself. They never write a child through `.pstack/package`; existing `safePath` symlink-parent rejection remains intact. Public installation continues using its existing copied package until the single cutover in #20, after journal activation, recovery and rollback pass.

## Internal activation journal

`prepareStagedActivation` stages a verified generation, resolves effective model configuration, and uses the shared preflight/planner. `applyStagedActivation` acquires the scope lock and every recorded/intended OpenCode-root lock before revalidating the preview. It rejects stale target or receipt observations before journaling or changing active paths. These APIs remain internal; the public installer still writes its previous layout.

Receipt schema 4 records the verified generation and effective rendering-input fingerprint. It owns the stable package link and host artifacts, with payload integrity verified through the retained descriptor rather than child writes through that link. Schemas 1–3 remain readable; the later public migration must explicitly handle their real package directory.

The single `.pstack/activation.json` journal contains operation ID, prior/intended receipts and generation, exact path before/after images (including backed-up file bytes/modes), newly created parent directories, state and completed-operation count. Each journal write uses an exclusive temporary file plus rename. Operations use temporary file/link plus rename, or remove a matching owned path, in deterministic order: stable package link first, sorted host operations, receipt last. Before each operation, observed state must match its recorded before or after image. Reapplying an already-completed image is safe. This is no promise of atomicity across host directories or consistency for already-running sessions.

States are `prepared`, `applying`, `verifying`, and `committed`. The receipt is published as the last path operation, then shared safe diagnostics/discovery run. A mandatory failure or diagnostic exception retains a `verifying` journal and its verified generation. Only passing verification permits the durable `committed` journal write, the success commit point. Journal cleanup follows that write; missing cleanup therefore does not turn a committed receipt into an absent installation. Progress can lag a completed filesystem operation after interruption, so recovery must inspect before/after values rather than trust the counter alone.

The injectable asynchronous boundary callback belongs only to internal tests. Subprocess tests exchange IPC acknowledgment before the parent sends a kill; there is no polling/sleep race and no CLI fault flag. Recovery execution is implemented in #18. Until then an interrupted internal fixture is accurately described but no runnable recovery command is advertised. The durability contract covers process crashes around completed filesystem operations. There is no power-loss guarantee, directory fsync protocol, transaction database, or live-session replacement guarantee.
