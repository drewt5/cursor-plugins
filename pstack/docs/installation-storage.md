# Internal retained package storage

`stagePackage({ source, root })` in `scripts/lib/installation-storage.mjs` copies only the portable payload into an unpredictable `.pstack/releases/.stage-*` directory on the installation filesystem. It preserves file modes, checks the canonical byte/executable-mode digest and source stability, writes detached provenance, and renames the complete payload to `.pstack/releases/<digest>`. It verifies all stored files and rejects symlinks, unexpected files, digest changes and provenance mismatches. An existing digest directory is inspected; its name alone is never proof. Reusing identical verified content retains that stored copy's provenance rather than inventing a new origin for unchanged bytes.

Staging does not publish a receipt, replace `.pstack/package`, activate host files, migrate legacy directories, or delete old releases. Failed staging removes only its own unpredictable scratch directory; it may leave empty storage parents. Callers will serialize mutation with the scoped installation lock. This internal API is not a public update command.

`verifyGeneration(root, generation)` validates a retained descriptor against the fixed local storage path. `renderStagedArtifacts({ root, generation, targets, opencodeRoot, global, config, hostObservations })` calls that verified payload's retained `scripts/lib/installation-artifacts.mjs:renderArtifacts` contract 1. It accepts the current effective model configuration and proposes artifacts without writing configuration or invoking providers. Only the supported current/previous generation and the explicit legacy migration baseline are recovery inputs; arbitrary historical renderer compatibility is not promised. Recovery execution uses the separate verified `scripts/recover.mjs` entry point. A captured legacy payload without a renderer is marked explicitly; it cannot regenerate configuration-derived adapters.

Proposed artifacts refer to the stable `.pstack/package` path, a relative link to the selected local generation. Host skill links, OpenCode command instructions and agent references use this location, so project relocation and source-checkout removal preserve references. Write operations use the real `.pstack/releases/<digest>` path and replace the stable link itself. They never write a child through `.pstack/package`; existing `safePath` symlink-parent rejection remains intact. Public installation continues using its existing copied package until the single cutover in #20, after journal activation, recovery and rollback pass.

## Internal activation journal

`prepareStagedActivation` stages a verified generation, resolves effective model configuration, and uses the shared preflight/planner. `applyStagedActivation` acquires the scope lock and every recorded/intended OpenCode-root lock before revalidating the preview. It rejects stale target or receipt observations before journaling or changing active paths. These APIs remain internal; the public installer still writes its previous layout.

Receipt schema 4 records the verified generation and effective rendering-input fingerprint. It owns the stable package link and host artifacts, with payload integrity verified through the retained descriptor rather than child writes through that link. Schemas 1–3 remain readable. Internal legacy fixtures now validate every owned payload path and move the real directory to an operation-specific backup before stable-link activation; the public migration ships in #20.

The single `.pstack/activation.json` journal contains operation ID, prior/intended receipts and generation, exact path before/after images (including backed-up file bytes/modes), newly created parent directories, state and completed-operation count. Each journal write uses an exclusive temporary file plus rename. Operations use temporary file/link plus rename, or remove a matching owned path, in deterministic order: stable package link first, sorted host operations, receipt last. Before each operation, observed state must match its recorded before or after image. Reapplying an already-completed image is safe. This is no promise of atomicity across host directories or consistency for already-running sessions.

States are `prepared`, `applying`, `verifying`, and `committed`. The receipt is published as the last path operation, then shared safe diagnostics/discovery run. A mandatory failure or diagnostic exception runs the same restoration engine; conflicting external edits retain the journal and verified recovery generation. Only passing verification permits the durable `committed` journal write, the success commit point. Journal cleanup follows that write; missing cleanup therefore does not turn a committed receipt into an absent installation. Progress can lag a completed filesystem operation after interruption, so recovery must inspect before/after values rather than trust the counter alone.

The injectable asynchronous boundary callback belongs only to internal tests. Subprocess tests exchange IPC acknowledgment before the parent sends a kill; there is no polling/sleep race and no CLI fault flag. The verified recovery executable and IPC crash coverage are described below. The durability contract covers process crashes around completed filesystem operations. There is no power-loss guarantee, directory fsync protocol, transaction database, or live-session replacement guarantee.


## Internal executable recovery

Before activation, persist a plain `.pstack/recovery.txt` instruction and print the exact `node '<verified-generation>/scripts/recover.mjs' --project '<scope>'` command. The candidate generation supplies this executable independently of the active package link and original checkout. The journal validates this identity and retains that generation until resolution. Legacy captures predating `release.json` retain byte identity and an observed manifest version, with original source/upstream/tag explicitly unknown; a missing old renderer is not fabricated.

`recoverInstallation` and `runStagedInstallation` reuse `recoverUnderLock`. An internal mutating run resolves an old journal before preparing a new plan. Pre-commit recovery checks every target against recorded before/after images, stops with exact conflicts and the runnable retry command on a third-party edit, restores in reverse order, and removes only empty parent directories it recorded as newly created. Failed post-activation diagnostics use this same engine. A fresh failure restores an absent installation; a legacy failure restores the exact moved directory and original receipt bytes/modes. User models, unrelated host registrations and provider executables are outside restoration.

Committed operations keep their intended receipt; recovery finishes cleanup only after confirming after images. An internally resolved journal is renamed to `.pstack/activation-completed.json` while external-root locks are still held. This is the same single journal in its cleanup location, not a history registry. It retains old/new XDG roots until those locks are released, then its operation ID is checked and the final instruction/journal cleanup happens under the scope lock. A kill in that window remains recoverable. Both journal locations at once are refused. Unknown temporary content or edited recovery instructions are preserved rather than deleted.

The actual retained CLI accepts `--recover-dead-locks`. It classifies every scope/recorded-root lock first, removes only demonstrably dead owners with matching tokens, and preserves all live or unverifiable owners. There is no age threshold, JSON editing requirement or instruction to delete `.pstack`. Doctor is read-only and reports `RECOVERY_REQUIRED`, `RECOVERY_CLEANUP_PENDING` or invalid evidence with next actions. The post-activation caller can identify its own locked journal so expected in-flight metadata does not fail its verification; the user doctor never supplies that internal identity.

The normal public installer remains on its earlier layout until #20. Recovery and legacy transition APIs are exercised internally without a public activation flag. Portable tests cover an exhaustive compact operation fixture through acknowledged subprocess kills, plus source-deleted fresh/legacy cases and multi-target/global XDG changes. They compare owned active bytes, modes, links, receipts and user content; staged storage and empty lock/setup parents are separate from the active snapshot. Process-crash recovery does not establish power-loss durability or live-session consistency.
